# Приложение для онлайн-бронирования столиков в ресторане
## 1 Общие сведения
## 1.1 Основание для выполнения работ
Программа развития сетей ресторанов.
## 1.2 Заказчик работ
Заказчик: Семейный ресторан "Маруся".
## 1.3 Цель выполнения работ
Работы по настоящему Договору выполняются с целью разработки и пилотного запуска веб-приложения, предоставляющего возможность онлайн-бронирования столиков в ресторане "Маруся".
## 1.4 Состав работ
По настоящему Договору Исполнитель выполняет перечисленные ниже работы:
1) разработка адаптивного веб-интерфейса для клиентов;
2) разработка веб-панели для администраторов ресторанов;
3) разработка серверной части приложения и API-сервиса для управления данными и бронированиями;
4) разработка базы данных для хранения информации о столиках, клиентах и бронированиях;
5) разработка технической документации.
## 1.5 Сроки выполнения работ
Срок выполнения работ - не более 90 дней с даты начала выполнения работ.
## 1.6 Место выполнения работ
Работы выполняются на территории Российской Федерации.
## 2 Назначение приложения для онлайн-бронирования столиков в ресторане
Веб-приложение для онлайн-бронирования столиков предназначено для предоставления клиентам ресторана "Маруся" возможности удаленного резервирования столиков с использованием веб-браузера.
Приложение должно предоставлять клиентам доступ к информации о ресторане, возможности выбора даты, времени и количества гостей, создания и отмены бронирования.
Для администраторов ресторана должно быть предусмотрено отдельное веб-интерфейсное средство, обеспечивающее просмотр информации о бронированиях и столиках.
Приложение должно обеспечивать разграничение доступа между клиентской и административной частью системы.
Веб-приложение должно быть адаптивным и обеспечивать возможность работы с персональных компьютеров, планшетов и мобильных устройств посредством современных веб-браузеров.
## 3 Описание услуги «Онлайн-бронирование столиков»
## 3.1 Схема предоставления услуги
Клиент посредством веб-браузера получает доступ к веб-приложению онлайн-бронирования столиков ресторана «Маруся». На главной странице приложения должна отображаться основная информация о ресторане, включая его наименование, адрес, часы работы и контактную информацию. Для выполнения бронирования клиент выбирает дату посещения, время и количество гостей. После этого система отображает столики, доступные для бронирования в выбранный период. Клиент выбирает подходящий столик, вводит необходимые контактные данные и подтверждает создание бронирования. После успешного создания бронирования система должна предоставить клиенту информацию о выполненной операции, включая дату, время, выбранный столик и идентификатор бронирования. Продолжительность одного бронирования в основной версии приложения составляет 2 часа.
Клиент должен иметь возможность отменить ранее созданное бронирование. Для отмены бронирования на главной странице приложения должна быть предусмотрена кнопка «Отменить бронирование», по нажатию на которую клиент вводит идентификатор бронирования, полученный им при подтверждении, и подтверждает отмену.
Администратор ресторана получает доступ к веб-интерфейсу администратора и может просматривать информацию о созданных бронированиях и занятости столиков.

## 3.2 Архитектура системы
Система состоит из следующих компонентов:
1) веб-интерфейс клиента (адаптивный, доступен с любых устройств);
2) веб-интерфейс администратора ресторана;
3) серверная часть (API-сервис);
4) база данных.
Веб-интерфейс клиента предназначен для просмотра информации о ресторане, выбора параметров бронирования, просмотра доступных столиков, создания и отмены бронирований.
Веб-интерфейс администратора предназначен для просмотра и управления бронированиями, а также для работы с информацией о столиках ресторана.
Серверная часть приложения обеспечивает обработку запросов от клиентского и административного интерфейсов, выполнение бизнес-логики приложения и взаимодействие с базой данных.
API-сервис обеспечивает обмен данными между веб-интерфейсами и серверной частью приложения.
База данных предназначена для хранения информации об администраторах, столиках, бронированиях и контактных данных клиентов, необходимых для функционирования приложения.

## 4 Требования к системе
## 4.1 Функциональные требования
Приложение должно предоставлять клиентам и администраторам ресторана следующие функциональные возможности.
### 4.1.1 Просмотр информации о ресторане
Клиент должен иметь возможность просматривать основную информацию о ресторане:
1) наименование ресторана;
2) адрес;
3) часы работы;
4) контактную информацию.
### 4.1.2 Просмотр доступных столиков
Клиент должен иметь возможность указать дату посещения, время посещения и количество гостей.
Система должна формировать список доступных столиков с учетом следующих условий:
1) вместимость столика должна быть не меньше указанного количества гостей;
2) столик не должен быть занят другим действующим бронированием в выбранный период времени.
Продолжительность одного бронирования в основной версии приложения составляет 2 часа.
Если подходящих столиков нет, система должна вывести соответствующее сообщение.
### 4.1.3 Создание бронирования
Клиент должен иметь возможность выбрать доступный столик и создать бронирование.
Для создания бронирования клиент вводит имя и номер телефона.
Дата, время, количество гостей и выбранный столик определяются на основании ранее выбранных параметров.
Перед созданием бронирования система должна повторно проверить доступность выбранного столика.
Если столик доступен, система должна:
1) сохранить бронирование в базе данных;
2) присвоить бронированию уникальный идентификатор;
3) вывести клиенту подтверждение создания бронирования.
Если выбранный столик уже занят другим бронированием, система не должна создавать новое бронирование и должна предложить клиенту выбрать другой столик.
### 4.1.4 Проверка конфликтов бронирования
Один и тот же столик не может иметь два действующих бронирования с пересекающимися временными интервалами.
Временные интервалы считаются конфликтующими, если они хотя бы частично пересекаются.
Если время окончания одного бронирования совпадает со временем начала другого бронирования, такие бронирования конфликтующими не считаются.
При создании бронирования система должна проверять его на пересечение с другими действующими бронированиями выбранного столика, само редактируемое бронирование в проверке пересечений не учитывается.
### 4.1.5 Отмена бронирования клиентом
Клиент должен иметь возможность отменить ранее созданное бронирование по его уникальному идентификатору.
После ввода идентификатора система должна найти соответствующее бронирование и отобразить информацию о нем.
После подтверждения отмены статус бронирования должен быть изменен на "отменено".
Отмененное бронирование не должно учитываться при определении доступности столика.
Если бронирование не найдено, уже было отменено или срок его действия истек, система должна вывести сообщение о невозможности отмены.
### 4.1.6 Авторизация и аутентификация администратора
Для доступа к административной части приложения администратор должен пройти авторизацию с использованием логина и пароля.
При успешной проверке данных система предоставляет доступ к веб-панели администратора.
При вводе неверного логина или пароля система должна вывести сообщение об ошибке и не предоставлять доступ к административной части.
### 4.1.7 Просмотр бронирований администратором
Администратор должен иметь возможность:
1) просматривать список бронирований;
2) просматривать информацию о каждом бронировании;
## 4.2 Нефункциональные требования
### 4.2.1 Требования к корректности данных
Приложение должно выполнять проверку вводимых пользователем данных.
Не должны сохраняться данные с незаполненными обязательными полями или недопустимыми значениями.
Количество гостей и вместимость столика должны быть положительными целыми числами.
Номер телефона клиента должен соответствовать допустимому формату.
Дата и время нового бронирования не должны находиться в прошлом.
### 4.2.2 Требования к пользовательскому интерфейсу
Приложение должно быть доступно пользователям посредством веб-браузера.
Интерфейс должен быть адаптивным и обеспечивать корректное отображение на персональных компьютерах, планшетах и мобильных устройствах.
При возникновении ошибок система должна выводить пользователю понятные сообщения.
### 4.2.3 Требования к сохранению данных
Информация о столиках, администраторах и бронированиях должна храниться в базе данных.
Информация о столиках включает в себя:
1) номер столика;
2) вместимость;
3) расположение или зона ресторана;
4) доступность столика.
Информация об администраторах включает в себя логин и пароль каждого администратора.
Информация о бронированиях включает в себя идентификатор бронирования.
Данные должны сохраняться после завершения работы и повторного запуска приложения.
Отмена бронирования не должна приводить к физическому удалению записи о нем из базы данных, статус бронирования должен измениться на "Отменено".
### 4.2.4 Требования к безопасности
Административная часть приложения должна быть недоступна неавторизованным пользователям.
Пароли администраторов не должны храниться в базе данных в открытом виде.
При возникновении ошибок пользователю не должна отображаться внутренняя техническая информация о системе.
### 4.2.5 Требования к структуре программного обеспечения
Приложение должно иметь модульную структуру.
Основные компоненты системы должны быть разделены таким образом, чтобы изменение одной функциональной части по возможности не требовало внесения несвязанных изменений в другие части приложения.
### 4.2.6 Требования к тестируемости
Основная функциональность приложения должна допускать автоматизированное тестирование.
Особое внимание должно уделяться проверке:
1) поиска доступных столиков;
2) соответствия вместимости столика количеству гостей;
3) создания бронирования;
4) пересечения временных интервалов;
5) повторной проверки доступности столика;
6) отмены бронирования;
7) запрета удаления столика с действующими бронированиями;
8) обработки некорректных входных данных.
## 4.3 Ограничения системы
В основной версии приложения:
1) обслуживается один ресторан;
2) клиентские учетные записи не создаются;
3) одно бронирование относится к одному столику;
4) продолжительность одного бронирования составляет 2 часа;
5) клиент самостоятельно выбирает конкретный доступный столик;
6) онлайн-оплата не предусматривается;
7) предварительный заказ блюд не предусматривается;
8) SMS- и email-уведомления не предусматриваются;
9) изменение бронирования не предусматривается;
10) используется одна административная роль;
11) мобильное приложение не разрабатывается.

## 5 Анализ аналога
## 5.1 Ближайший аналог
Ближайшим аналогом разрабатываемого приложения является сервис онлайн-бронирования Restoclub — агрегатор ресторанов, где бронирование столика выполняется через веб-сайт. Как и в нашем приложении, клиент выбирает ресторан, дату, время и количество гостей и получает подтверждение брони.
Ключевые особенности аналога:
1) сервис объединяет множество ресторанов, а не один;
2) для бронирования, как правило, требуется регистрация или подтверждение номера телефона по SMS;
3) столик обычно назначается рестораном, а не выбирается клиентом;
4) часть функций (депозиты, акции, отзывы) ориентирована на маркетинг агрегатора, а не на потребности одного заведения.
## 5.2 Сравнение с разрабатываемым приложением
| Возможность | Restoclub | Приложение «Маруся» |
|---|---|---|
| Регистрация клиента | Обычно требуется | Не требуется |
| Выбор конкретного столика клиентом | Как правило, нет | Да, с указанием вместимости и зоны |
| Отмена брони | Через личный кабинет или по звонку | По идентификатору брони, без аккаунта |
| Проверка конфликтов интервалов | Скрыта от пользователя | Реализована и покрыта автотестами (2 часа, граница интервалов не считается конфликтом) |
| Повторная проверка доступности перед созданием | Не раскрывается | Обязательна |
| Админ-панель | Единый кабинет для множества ресторанов | Отдельная панель, ориентированная на один ресторан |
| Персонализация под заведение | Ограничена шаблоном агрегатора | Полная (данные о ресторане, столиках, зонах) |
| Хранение отменённых броней | Не раскрывается | Не удаляются, статус «отменено» |
## 5.3 Преимущества разрабатываемого приложения
1) Простота для клиента: не нужно регистрироваться, достаточно указать имя и телефон;
2) Осознанный выбор столика: клиент сам выбирает подходящий столик по вместимости и расположению;
3) Отмена без личного кабинета: достаточно идентификатора брони;
4) Надёжность бронирования: повторная проверка доступности и защита от пересекающихся интервалов;
5) Сохранность истории: отменённые брони остаются в базе со статусом «отменено»;
6) Независимость от агрегатора: ресторан сам управляет данными и интерфейсом;
7) Тестируемость: ключевая логика покрыта автоматическими тестами.
## 5.4 Недостатки относительно аналога
В приложении не предусмотрены SMS- и email-уведомления, онлайн-оплата, отзывы и мультиресторанный каталог. Это осознанные ограничения основной версии.

## 6 Состав и содержание работ по развертыванию
## 6.1 Требования к выполнению развертывания
Развертывание веб-приложения онлайн-бронирования столиков должно выполняться на серверной инфраструктуре, предназначенной для размещения программных компонентов системы.
В процессе развертывания должны быть выполнены следующие работы:
1) установка и настройка серверной части веб-приложения;
2) установка и настройка системы управления базой данных;
3) размещение и настройка клиентской части веб-приложения;
4) настройка подключения серверной части к базе данных;
5) создание и настройка учетной записи администратора;
6) первоначальное заполнение базы данных сведениями о ресторане и столиках;
7) настройка учетных данных к базе данных и URL-ссылки на сайт с бронированием;
8) проверка корректности взаимодействия основных компонентов веб-приложения;
9) проверка доступности веб-приложения для пользователей через веб-браузер.
Развертывание должно предусматривать наличие тестовой среды, предназначенной для проведения испытаний и проверки работоспособности веб-приложения, и рабочей среды, предназначенной для непосредственного использования системы. Опытная эксплуатация веб-приложения должна проводиться в рабочей среде после завершения первоначальной настройки и успешного прохождения предварительных испытаний. При развертывании должны быть обеспечены сохранность и корректность данных, хранящихся в базе данных. При необходимости должны предусматриваться средства резервного копирования базы данных.
## 6.2 Порядок выполнения развертывания
Развертывание веб-приложения должно выполняться поэтапно. На первом этапе выполняется подготовка серверной инфраструктуры, установка необходимых программных компонентов и системы управления базами данных. На втором этапе выполняется установка серверной, клиентской и административной частей веб-приложения, настройка API и соединения с базой данных. На третьем этапе выполняется первоначальная настройка системы, включающая создание учетной записи администратора, внесение сведений о ресторане и столиках, а также настройку параметров, необходимых для работы системы. На четвертом этапе выполняется проверка работоспособности основных функций веб-приложения в тестовой среде.
После устранения выявленных ошибок и получения положительных результатов тестирования система может быть развернута в рабочей среде.
## 6.3 Результат выполнения работ по развертыванию
Результатом выполнения работ по развертыванию должно являться работоспособное веб-приложение онлайн-бронирования столиков, включающее:
1) клиентскую часть веб-приложения;
2) административную часть веб-приложения;
3) серверную часть;
4) базу данных;
5) все тесты прошли успешно, выдали код 200.
После завершения развертывания пользователь должен иметь возможность получить доступ к веб-приложению посредством веб-браузера и выполнить предусмотренные ТЗ операции, а администратор — получить доступ к административной части системы.
## 7 Порядок контроля и приемки
Контроль и приемка веб-приложения должны осуществляться в соответствии с требованиями настоящего Технического задания и разработанной Программой и методикой испытаний. Порядок контроля предусматривает проведение:
1) предварительных испытаний;
2) опытной эксплуатации;
3) приёмо-сдаточных испытаний.
## 7.1 Предварительные испытания
Предварительные испытания веб-приложения проводятся с целью проверки соответствия реализованной системы требованиям настоящего Технического задания.
Испытания должны проводиться согласно разработанной Программе и методике испытаний.
| Название испытания | Порядок действий | Ожидаемый результат |
|---|---|---|
| Просмотр пользователем информации о ресторане | Открыть главную страницу веб-приложения | Отображается наименование ресторана, адрес, часы работы и контактная информация |
| Выбор даты и времени посещения, указание количества гостей | На главной странице указать дату, время посещения и количество гостей | Введённые значения корректно принимаются системой и используются для дальнейшего поиска столиков |
| Просмотр доступных для бронирования столиков | После указания даты, времени и количества гостей отправить запрос на поиск столиков | Система отображает список столиков, свободных на выбранный период и подходящих по вместимости |
| Проверка доступности выбранного столика | Выбрать столик из списка и перейти к оформлению бронирования | Перед созданием бронирования система повторно проверяет, что столик свободен на выбранный период |
| Создание бронирования | Ввести контактные данные (имя, телефон) и подтвердить бронирование доступного столика | Бронирование создаётся и сохраняется в базе данных |
| Формирование идентификатора бронирования | Создать бронирование | Системой присваивается уникальный идентификатор бронирования, который отображается клиенту |
| Предотвращение создания нескольких бронирований одного столика на одно и то же время | Попытаться забронировать столик, уже занятый другим действующим бронированием на пересекающийся период | Система отклоняет создание нового бронирования и сообщает о недоступности столика |
| Подтверждение созданного бронирования | Успешно создать бронирование | Клиенту выводится подтверждение с указанием даты, времени, столика и идентификатора бронирования |
| Просмотр информации о созданном бронировании | Запросить данные о бронировании по идентификатору | Система отображает корректную информацию о найденном бронировании |
| Отмена бронирования | Ввести идентификатор существующего действующего бронирования и подтвердить отмену | Бронирование отменяется, клиенту выводится подтверждение отмены |
| Изменение статуса отменённого бронирования на «отменено» | Отменить бронирование и проверить его статус в базе данных | Статус бронирования изменён на «отменено», запись физически не удалена |
| Сохранение информации о бронировании в базе данных | Создать бронирование, перезапустить приложение и повторно запросить данные о бронировании | Данные о бронировании сохраняются и доступны после перезапуска системы |
| Авторизация администратора | Ввести корректные логин и пароль на странице авторизации администратора | Администратору предоставляется доступ к веб-панели администратора |
| Просмотр администратором информации о бронированиях | Авторизоваться и открыть раздел просмотра бронирований | Отображается список бронирований с данными о столиках, дате, времени и контактах клиентов |
| Проверка корректности обработки ошибочных и неполных данных | Ввести некорректные данные (пустые поля, неверный формат телефона, неверный логин/пароль и т.п.) | Система выводит понятное сообщение об ошибке и не сохраняет некорректные данные |
| Проверка взаимодействия клиентской, серверной частей и базы данных | Выполнить полный сценарий бронирования от клиентского интерфейса до сохранения записи в базе данных | Данные корректно передаются между компонентами системы, итоговый результат соответствует ожидаемому на каждом этапе |
## 7.2 Опытная эксплуатация
Опытная эксплуатация веб-приложения проводится с целью проверки его работоспособности в реальных либо приближенных к реальным условиях эксплуатации.
В процессе опытной эксплуатации должны проверяться:
1) корректность отображения информации о ресторане и столиках;
2) возможность создания бронирования пользователем;
3) корректность определения доступности столиков;
4) отсутствие возможности одновременного бронирования одного столика на одинаковые дату и время;
5) корректность подтверждения бронирования;
6) корректность отмены бронирования;
7) сохранение отменённого бронирования в базе данных со статусом «отменено»;
8) корректность отображения бронирований в административной части;
9) корректность авторизации администратора;
10) корректность обработки некорректных данных;
11) устойчивость работы веб-приложения при выполнении основных пользовательских операций.
В процессе опытной эксплуатации выявленные замечания должны фиксироваться и устраняться Исполнителем.
По завершении опытной эксплуатации должен быть оформлен Отчёт о проведении опытной эксплуатации.
Решение о возможности проведения приёмо-сдаточных испытаний принимается после подтверждения работоспособности веб-приложения и соответствия его функциональности требованиям настоящего Технического задания.
## 7.3 Приёмо-сдаточные испытания
Приёмо-сдаточные испытания проводятся с целью окончательной оценки результатов разработки и опытной эксплуатации веб-приложения и определения соответствия системы требованиям настоящего Технического задания. Испытания проводятся согласно Программе и методике приёмо-сдаточных испытаний, разработанной в рамках выполнения работ. В ходе приёмо-сдаточных испытаний должна быть подтверждена работоспособность основных функций веб-приложения, в том числе:
1) просмотра информации о ресторане;
2) просмотра доступных столиков;
3) создания и подтверждения бронирования;
4) предотвращения конфликтующих бронирований;
5) отмены бронирования;
6) изменения статуса бронирования на «отменено»;
7) сохранения данных о бронированиях;
8) работы административной части;
9) авторизации администратора;
10) корректного взаимодействия с базой данных.
<br> В случае выявления несоответствий или нарушения заявленной функциональности испытания могут быть приостановлены с оформлением соответствующего протокола. Выявленные неисправности и несоответствия должны быть устранены Исполнителем. После устранения выявленных недостатков приёмо-сдаточные испытания должны быть проведены повторно. В случае отсутствия замечаний и подтверждения соответствия веб-приложения требованиям настоящего Технического задания составляется Акт о проведении приёмо-сдаточных испытаний и сдаче-приёмке выполненных работ.
